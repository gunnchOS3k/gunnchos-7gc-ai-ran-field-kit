# Program Operating Model

## Purpose

The program is now mature enough that the primary risk is overengineering evidence, allowing architecture drift, running too much in parallel, and delaying contact with reality.

Optimize for:
- independent verification;
- depth before breadth;
- risk-first selection;
- bounded work packets;
- accepted-main truth;
- frozen configurations;
- early EVT and human evaluation;
- product quality;
- economics/supply/licensing/security;
- field feedback.

## Product truth hierarchy

```text
1. accepted owner-repo implementation
2. owner-repo tests/evidence
3. independent verifier evidence
4. accepted-main golden journey evidence
5. release configuration
6. control-plane aggregation
```

## Parallel work

At most:
- Lane A: OS/software/platform
- Lane B: AI/application/product quality
- Lane C: hardware/external/EVT

## Authority

Edmund controls:
- merges;
- Class D/E approvals;
- external sends;
- purchasing/fabrication;
- NDA/contracts;
- release configuration approval.

Automation may implement/test/open draft PRs, but never self-authorize these actions.

## Broad-prompt freeze

```text
BROAD_COMPLETION_PHASES = FROZEN
```

New broad phases require a material charter/product/standards redesign.
